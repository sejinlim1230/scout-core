# Scout Core

V:Scout의 검증된 업무 흐름을 기반으로 만든 재사용 가능한 기본 뼈대입니다. 현재 운영 중인 회사 V:Scout와 데이터가 연결되지 않는 독립적인 데모 버전입니다.

## 실행

`index.html`을 브라우저에서 열면 됩니다. 로컬 서버가 필요하다면 이 폴더에서 `python -m http.server 8080`을 실행한 후 `http://localhost:8080`으로 접속합니다.

## 프로젝트별로 바꿀 곳

1. `config.js`: 서비스명, 팀원, 단계, 메뉴, 미연락 기준일
2. `data.js`: 현재 데모 저장소를 Supabase 저장소로 교체
3. `styles.css`: 브랜드 색상과 레이아웃 토큰
4. `app.js`: 프로젝트별 화면과 KPI 계산

## 엑셀 내보내기

상단의 `엑셀 내보내기` 버튼에서 전체 데이터 또는 현재 기관 검색 결과를 `.xlsx`로 다운로드할 수 있습니다. 기본 통합문서는 `요약`, `기관 목록`, `후속 액션` 시트로 구성됩니다. 운영 환경에서는 내보내기 기능을 관리자 권한으로 제한하고 감사 로그를 기록하세요.

화면은 `scoutData.loadSnapshot()`, `addOrg()`, `toggleAction()`만 호출합니다. Supabase 마이그레이션 시 화면 코드를 직접 고치지 않고 이 데이터 경계만 교체하는 것이 핵심입니다.

## 개인 계정 기반 권장 구조

- 개인 GitHub: 소스 코드와 버전 관리
- 개인 Supabase 개발 프로젝트: 익명화한 개발·검증 데이터
- 회사 Supabase 운영 프로젝트: 실제 개인정보와 운영 데이터
- 개인 Notion: 제품 허브, 결정 기록, KPI 사전, 마이그레이션 로그
- 회사 Notion: 운영 매뉴얼과 실제 업무 절차

실제 개인정보를 개인 프로젝트에 그대로 복사하지 마세요. 개발 데이터는 기관명·담당자·연락처를 익명화하고 최소한의 샘플만 사용합니다.

## 마이그레이션 순서

1. 현재 DB 스키마와 KPI 정의를 동결하고 백업합니다.
2. 회사 운영본과 개인 개발본의 환경 변수를 분리합니다.
3. 개인 Supabase에 스키마만 먼저 적용합니다.
4. 익명화된 샘플 데이터로 기능을 검증합니다.
5. 기능별로 `orgs → actions → contact_logs → talents → applications → jobs` 순서로 어댑터를 연결합니다.
6. 각 단계에서 행 수, 외래키, KPI 결과를 구·신 시스템 간 비교합니다.
7. 쓰기 기능은 조회 검증이 끝난 모듈부터 하나씩 엽니다.
8. 최종 전환 전 권한(RLS), 감사 로그, 백업·복구 절차를 검증합니다.

## V:Scout에서 우선 개선할 항목

- 데이터 로딩 실패를 빈 배열 또는 0건으로 표시하지 않기
- 동일 의미 KPI 카드 중복 제거와 KPI 정의 상시 노출
- `innerHTML`에 사용자 입력을 직접 삽입하지 않고 이스케이프 또는 DOM API 사용
- 저장 버튼 중복 클릭 방지, 저장 중 상태, 성공·실패 피드백 제공
- 사이드바를 핵심 업무와 보조 관리 기능으로 재분류
- 모바일에서 등록보다 조회·빠른 기록 흐름을 우선 배치
- 한 번에 모든 테이블을 읽기보다 화면별 로딩과 상세 로딩 분리
- 운영 데이터에는 RLS와 최소 권한 원칙 적용
